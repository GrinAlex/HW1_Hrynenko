# ReAct-агент для роботи відділу маркетингу з ціновими акціями

## 1. Опис проєкту

Проєкт реалізує автономного ReAct-агента на базі **LangGraph** для автоматизації роботи спеціаліста відділу маркетингу з управління ціновими акціями та промокодами. Агент працює на базі локальної LLM `llama3.1:8b` через Ollama (OpenAI-сумісний API `ChatOpenAI`) з можливістю перемикання на хмарний провайдер OpenRouter (`openai/gpt-4o-mini`). Ключові можливості: пошук, створення та деактивація акцій із суворою Pydantic v2 валідацією, формування структурованих відповідей (`structured outputs`), захист від зациклення й перевищення лімітів та повне JSON-логування траєкторії виконання.

## 2. Доменна задача

- **Домен:** маркетинг (управління ціновими акціями та промокодами).
- **Що вирішує агент:** обробляє запити щодо перегляду активних акцій за категоріями, запуску нових промокампаній із дотриманням бізнес-обмежень (максимальна знижка ≤ 70%, коректний порядок дат, формат і унікальність промокоду) та дострокової зупинки діючих акцій.
- **Інструменти (tools):**
  - `search_promos` — шукає наявні цінові акції за категорією (`electronics`, `clothing`, `home`, `all`) та статусом активності (`only_active`).
  - `create_promo` — створює нову цінову акцію або промокод (валідує формат `^[A-Z0-9_]+$`, знижку 1–70% та крос-умову `end_date > start_date`).
  - `deactivate_promo` — достроково деактивує діючу акцію за промокодом із обов'язковою фіксацією причини зупинки.

## 3. Архітектура

- **LLM-провайдер:** `langchain_openai.ChatOpenAI`, підключений до локального сервера Ollama (`http://localhost:11434/v1`, модель `llama3.1:8b`, `temperature=0.1`). Конфігурація винесена в `.env` (підтримується OpenRouter).
- **Структура графа (`agent.py`):** `StateGraph(AgentState)` з трьома вузлами:
  - `agent` — викликає LLM із прив'язаними інструментами (`bind_tools`) і перевіряє захисні обмеження.
  - `tools` — обгортка над `ToolNode(TOOLS_LIST, handle_tool_errors=True)` для виконання tool calls.
  - `formatter` — формує фінальну структуровану відповідь за Pydantic-моделлю `PromoAgentResponse` (`answer`, `confidence`, `sources`) через `with_structured_output` (із безпечним fallback).
  - **Conditional edge (`should_continue`):** якщо є `tool_calls` і не спрацював `stop_reason` → перехід у `tools` (і далі назад в `agent`); інакше → перехід у `formatter` → `END`.
- **Захисні механізми (`safety.py`):**
  - `MAX_STEPS = 10` — обмеження максимальної кількості ітерацій циклу.
  - `TIMEOUT_SECONDS = 90` — загальний тайм-аут виконання (на базі `time.monotonic()`).
  - `LoopDetector(max_repeats=3)` — детекція зациклення за MD5-хешем назви інструменту та його аргументів.
- **Логування (`logger.py`):** `TrajectoryLogger` фіксує кожен крок вузлів (`step`, `node`, `input`, `output`, `tool_calls`, `timestamp`, `elapsed_ms`) у файл `trajectory.json`.

## 4. Інструкція запуску

1. Клонувати репозиторій:

   ```bash
   git clone <repo-url>
   cd hw1_react_agent
   ```

2. Створити віртуальне середовище та встановити залежності:

   ```bash
    python -m venv .venv
    source .venv/bin/activate  # для Windows: .venv\Scripts\activate
    pip install -r requirements.txt
   ```

3. Налаштувати .env (обрати локальну Ollama або розкоментувати OpenRouter):
   ```
   LLM_BASE_URL=http://localhost:11434/v1
   LLM_API_KEY=ollama
   LLM_MODEL=llama3.1:8b
   ```

4. Переконатися, що Ollama запущено та модель завантажено.

   ```bash
    ollama pull llama3.1:8b
   ```

5. Запустити unit-тести, перевірку захисних механізмів та E2E тест-кейси
   ```bash
    python test_runner.py
   ```

## 6. Аналіз результатів

**Чи правильно агент обирав tools?**
У всіх 4 тест-кейсах агент коректно підбирав інструменти та їхні параметри під запит. У TC-001 викликано search_promos, у TC-002 — search_promos та create_promo, а у складному TC-004 агент за один крок сформував коректний ланцюжок із трьох інструментів (search_promos, deactivate_promo, create_promo), виконавши всі частини запиту.

**Де агент помилявся і чому?**
Критичних помилок виконання чи галюцинацій параметрів не зафіксовано, проте аналіз trajectory.json для TC-004 виявив неточність на етапі вузла formatter: локальна модель llama3.1:8b під час генерації structured output помістила список використаних інструментів у текстове поле answer, а в поле sources записала ["Текст"]. Також у відповіді TC-001 трапилася незначна лексична калька («Дискаунт» замість «Знижка»). Це типова поведінка компактних 8B-моделей при суворому JSON-форматуванні українською мовою.

**Кроки: simple vs complex.**
У всіх чотирьох тест-кейсах агент виконав задачу за 2 кроки вузла agent (крок 1 — планування та виклик інструментів, крок 2 — формування фінальної відповіді). Лінійної залежності кількості кроків від складності не спостерігалося, оскільки llama3.1:8b підтримує паралельний tool calling і в TC-002 та TC-004 викликала всі необхідні інструменти за одну ітерацію.

**Чи досягав агент max_steps або timeout?**
Ні, у жодному тесті ліміти не були досягнуті. Фактична кількість кроків (2) була в 5 разів меншою за MAX_STEPS = 10, а максимальний час виконання (17.2 с у TC-004) — значно меншим за TIMEOUT_SECONDS = 90. Коректність спрацювання LoopDetector і timeout підтверджено окремими unit-тестами в test_runner.py.

**Залежність часу виконання від складності.**
Час виконання загалом зростав зі збільшенням обсягу контексту та кількості інструментів: від 13.3 с (TC-001) до 17.2 с (TC-004). Винятком став TC-003 (6.6 с), де відповідь і виклик інструменту були найкоротшими. Згідно з trajectory.json (TC-004), самі інструменти виконуються миттєво (~3 мс), тоді як основну затримку створює локальний інференс LLM: ~4.9 с на вибір інструментів, ~5.2 с на фінальну відповідь та ~7.1 с на вузол formatter.

**Випадки, коли агент НЕ використав tool, хоч мав би.**
У TC-003 (запит створити MEGA_DROP зі знижкою 85% або максимально можливою) агент коректно обмежив знижку до 70% і створив акцію, але пропустив виклик search_promos, хоча системний промпт вимагає перевіряти наявні акції перед створенням нової. Це свідчить про те, що коли в запиті немає явного прохання «перевір акції», 8B-модель може ігнорувати фонові правила із системного промпту.

## 7. Висновки та обмеження

- Що працює добре: ReAct-цикл у LangGraph із паралельним викликом інструментів, Pydantic v2 валідація (extra="forbid", @field_validator, @model_validator), захисні механізми (max_steps, timeout, LoopDetector) та детальне логування траєкторії в trajectory.json.
- Що можна покращити: заповнювати поле sources у formatter_node програмно (зі стану графа), а не покладатися на LLM; винести збереження акцій із in-memory словника PROMO_DB у SQLite/PostgreSQL; для складних бізнес-правил використовувати потужнішу модель (наприклад, через OpenRouter).
- Відомі обмеження: дані в PROMO_DB не зберігаються між перезапусками скрипта; якість дотримання неявних інструкцій системного промпту та чистота української мови залежать від розміру локальної моделі (llama3.1:8b).

## 8. Структура файлів

- `tools.py` — Pydantic v2 схеми, валідатори та 3 інструменти (search_promos, create_promo, deactivate_promo).
- `agent.py` — LangGraph StateGraph (agent, tools, formatter) та structured outputs (PromoAgentResponse).
- `safety.py` — захисні механізми: MAX_STEPS, TIMEOUT_SECONDS, is_timeout_exceeded, LoopDetector.
- `logger.py` — TrajectoryLogger для збереження траєкторії у JSON.
- `test_runner.py` — unit-тести інструментів/захисту та прогін 4 E2E тест-кейсів.
- `trajectory.json` — JSON-лог повної траєкторії виконання агента (генерується).
- `test_results.json` — результати тестування 4 тест-кейсів (генерується).
- `requirements.txt` — список Python-залежностей.
- `.env / .env.example` — налаштування підключення до Ollama / OpenRouter.
- `README.md` — документація проєкту, інструкція запуску та аналіз результатів.
